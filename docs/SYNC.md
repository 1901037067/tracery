# EVNote 同步设计（v2）

> 目标：**数据在自己手里**，同时保证「无论怎么冲突，都不丢用户的字」。
> v2 在文件级同步之上加了三方文本合并与大文件分块续传；端到端加密在 v3。

## 1. 角色划分

```
 ┌────────────┐    HTTP     ┌──────────────┐    HTTP     ┌────────────┐
 │ 设备 A      │ ──────────▶ │  evnote-sync │ ◀────────── │ 设备 B      │
 │ Node 服务端 │             │  （NAS 等）   │             │ Node 服务端 │
 │  └ 文件系统 │             └──────────────┘             └ 文件系统    │
 └────────────┘
```

| 角色 | 职责 | 不做什么 |
|---|---|---|
| 设备端 `server/sync.js` | 计算 sha、三方比对、传输、写盘、产生冲突副本 | 不解析 Markdown |
| 同步服务端 `sync-server/` | 存 blob + 版本化清单、校验哈希、鉴权 | 不理解笔记、不知道双链/标签 |

把同步放在 Node 主进程侧而不是浏览器，原因有两个：浏览器没有文件系统权限；以及**token 不该出现在前端**——渲染进程只知道「同步进行到哪一步」。

## 2. 存储模型

```
<data>/config.json                 vaultId / 配对码 / 设备 token
<data>/<vaultId>/manifest.json     { version, files: { relPath: { sha, size, mtime } } }
<data>/<vaultId>/blobs/<sha256>    文件内容，按内容寻址
```

- **内容寻址**：blob 名就是内容哈希，同内容天然去重；传输损坏会被服务端当场拒绝（重算哈希比对）
- **清单版本号**单调递增，每次 commit +1，用作乐观锁
- 服务端只认识「路径 → sha」这一层，所以 v3 加加密时只需把 blob 换成密文、路径换成 HMAC，接口不变

## 3. 同步算法（三方比对）

每次同步取三份数据：

- `local`：当前仓库快照（sha256）
- `remote`：服务端清单
- `base`：上次同步成功时记录的 sha（存在仓库的 `.evnote/sync-state.json`）

`base` 是关键——它回答「这个文件到底是谁改的」，而不是简单比较新旧时间。

| local | remote | base | 判定 | 动作 |
|---|---|---|---|---|
| = remote | | | 两边一致 | 无操作 |
| = base | ≠ base | | **只有远端改** | 下载（remote 为空 → 本地进回收站） |
| ≠ base | = base | | **只有本地改** | 上传（local 为空 → 提交删除） |
| ≠ base | ≠ base | 有 | **两边都改** | 冲突：本地留原路径，远端写副本，副本也上传 |
| 有 | 有 | 无 | **首次同步双方都有** | 同冲突处理（不猜谁的版本更"新"） |
| 有 | 无 | 有 | 远端删 + 本地改 | 保留本地并重新上传（宁可复活，不丢内容） |
| 无 | 有 | 有 | 本地删 + 远端改 | 恢复远端（同上） |

### 为什么不用「修改时间更新者胜」

跨设备时钟几乎不可能一致（时区、手动改时间、休眠唤醒），用 mtime 判定迟早会出现「新版本被旧版本覆盖」。sha + base 不依赖时钟。

### 自动合并（v2）

两边都改过时，先尝试三方合并，而不是直接生成副本：

```
base（上次同步的内容，从服务端 blob 取）
   ├── ours   本地当前内容
   └── theirs 远端当前内容
        ↓ node-diff3（diff3Merge，excludeFalseConflicts）
   没有冲突 → 写入合并结果、上传、更新 base（两台设备最终看到同一份）
   有冲突   → 放弃合并，走下面的「冲突副本」策略（不写半成品）
```

- 只对 `.md` / `.markdown` / `.txt` 生效；图片、PDF、压缩包一律走副本
- 两边把同一处改成**完全相同**的内容，不算冲突
- 行尾跟随 base：CRLF 的笔记合并后仍是 CRLF
- 判定偏保守：**追加内容紧挨着对方修改过的最后一行**时也会判冲突——宁可多一个副本，也不猜

### 冲突副本的样子

```
笔记甲.md                                  ← 保留你本地版本
笔记甲 (冲突 设备B 20261017-030305).md      ← 另一台设备的版本，同样上传到服务器
```

副本会作为普通文件参与后续同步，所以**两台设备最终都能看到两份内容**。UI 会在设置 → 同步里列出本次产生的副本。

## 4. 提交与并发

```
POST /api/commit { baseVersion, changes: [{ path, sha, size, mtime } | { path, deleted: true }] }
```

- 服务端只在 `baseVersion === manifest.version` 时接受，否则返回 409
- 客户端遇到 409 会重新拉清单、重算差异（最多 3 轮）
- 因此**不会出现「A 刚推上去的内容被 B 用旧清单覆盖」**——B 的提交会被拒，然后它就会看到 A 的新版本并按冲突规则处理

## 5. 大文件传输（v2）

| 场景 | 做法 |
|---|---|
| 上传 < 4MB | 一次 `PUT /api/blob/:sha` |
| 上传 ≥ 4MB | `init` 建会话 → 1MB 分块 `PUT /api/upload/:id/:index` → `complete` 拼装校验 sha |
| 断点续传 | 重新 `init` 时服务端返回已有块（或 `GET /api/upload/:id`），客户端只补缺失块；每块失败重试 3 次 |
| 下载 | 服务端支持 `Range: bytes=`（206），客户端先写 `*.evnote-tmp`，中断后从已下载长度继续 |
| 完整性 | 单块拼装完成后重算 sha256，与声明不符直接拒绝并清理会话 |

上传会话存在 `<data>/<vaultId>/uploads/<id>/`，24 小时无活动自动清理。

## 6. 写入安全

- 下载先写 `*.evnote-tmp` 再 `rename`，避免半截文件
- 远端删除不直接 `unlink`，而是移到 `<vault>/.evnote/trash/<时间戳>/<原路径>`
- 同步刚写完文件的 2.5 秒内，文件监听器的事件被忽略，防止「写盘 → 触发同步 → 再写盘」自激
- 单文件上限 100MB（`server/sync.js` 的 `MAX_FILE`），超限跳过而不是把内存打爆

## 7. 自动同步的触发

| 触发 | 时机 |
|---|---|
| 启动 | 服务端启动后若已配对，按 `interval` 起定时器 |
| 本地改动 | 文件监听 120ms 合并 → 再延迟 4 秒（避开打字中的半成品） |
| 定时 | 默认 60 秒（可设 30 秒 / 5 分钟 / 关） |
| 手动 | 设置 → 同步 → 立即同步 |

同一时刻只允许一个同步任务（`running` 复用同一个 Promise），避免两个任务互相踩。

## 7b. 局域网直连（免部署）

两台设备在同一个 Wi-Fi 里就能同步，不需要单独跑服务端：

```
主机设备                                其他设备
┌────────────────────────┐             ┌──────────────────────┐
│ 内嵌 sync-server（随机端口）│ ◀── UDP ──│ 广播 { 6 位通行码 }    │
│ UDP 应答 47891-47893    │ ──应答──▶  │ 逐个试 IP 直到 health 通 │
│ 自己的引擎也连上来        │             │ 配对 → 正常同步引擎      │
└────────────────────────┘             └──────────────────────┘
```

- 主机点「本机当主机」→ 生成 6 位数字通行码；每次开启都重新生成
- 其他设备输入通行码 → UDP 广播发现 → 自动配对（换 token）→ 走同一套同步引擎
- 主机的引擎也指向内嵌服务端，所以合并/冲突/回收站等行为与外置服务端完全一致
- 停止共享 = 断开引擎 + 关闭内嵌服务端，本地笔记不动
- 发现协议在 `server/lan.js`，端口 47891-47893；被防火墙拦住时仍可手动填 `http://<主机IP>:<端口>`

## 8. 安全边界（如实说明）

- 传输是 HTTP 明文，默认只监听局域网。公网请套 HTTPS 反代或用 Tailscale/WireGuard
- 服务端能读到明文内容（v3 才做 E2E）
- 配对码等同于「允许新设备加入」，配对完成后可在服务端重建 `pairCode`
- token 不返回给前端；`/api/sync/status` 只回连接状态
